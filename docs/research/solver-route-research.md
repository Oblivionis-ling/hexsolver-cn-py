# Hexcells 求解器设计路线调研

> 历史研究文档：写于 2026-04，2026-08-05 迁入仓库。项目已经从截图/OCR 原型转向精确种子生成，当前路线以 [`../../DEVELOPMENT_HISTORY.md`](../../DEVELOPMENT_HISTORY.md) 为准。

这份文档回答三个问题：

1. 如果我们要做一个 `Hexcells / Hexcells Infinite` 求解器，最合理的设计路线是什么？
2. 已经有哪些开源案例可以参考？
3. 哪些方向应该优先，哪些方向不该一上来就碰？

这份文档默认配合前一份[规则笔记](./hexcells-infinite-rules.md)一起看。

## 1. 先给结论

如果我们现在开始做，我建议按下面顺序推进：

1. 先做“**抽象盘面求解核心**”，不要先做 OCR。
2. 第一版输入优先支持 `SixCells` 的 `.hexcells` 文本格式，先把逻辑求解打通。
3. 求解器第一阶段目标定为“**找出当前盘面所有必然格**”，不是“像人一样解释每一步”。
4. 在求解核心稳定之后，再决定是否做：
   - 截图/OCR 导入
   - 实时辅助官方游戏
   - 自动点击
   - 人类可读推理解释

一句话版本：

**最稳的路线是“先约束求解器，后图像识别器”，而不是反过来。**

## 2. 是否已经有开源案例？

有，而且至少有两个很值得参考的成熟方向。

### 2.1 SixCells

仓库：<https://github.com/oprypin/sixcells>

它是什么：

- 一个开源的 `Hexcells` 关卡编辑器/播放器
- 支持把关卡以 `.hexcells` 文本格式导入、分享、游玩
- 自带“full auto-solving capabilities”

对我们最有价值的地方：

- 它证明了：**纯逻辑求解器是能做出来的**
- 它把盘面落在一个简单、可解析的文本格式里，特别适合做测试输入
- README 明确写了它用 `PuLP` 做求解
- `solver.py` 里能看到它把未知格压缩成等价类，并把提示转成线性约束，再调用整数规划求解

它对我们意味着什么：

- 如果目标是先做“会解题”的核心，这条路线已经被验证过
- 不需要先碰屏幕识别，也不需要先逆向官方存档或 Unity 资源

注意事项：

- `SixCells` 的许可证是 `GPLv3`
- 可以学习思路和做法
- 但如果未来希望我们自己的实现用更宽松许可证，**不要直接拷代码**

### 2.2 HexSolver

仓库：<https://github.com/Mikescher/HexSolver>

它是什么：

- 一个面向官方游戏窗口的自动求解器
- README 明确写了目标是自动解析游戏状态、找出下一步并执行
- 支持 `Hexcells`、`Hexcells Plus`、`Hexcells Infinite`

它做了什么：

- 自动截取游戏窗口
- 动态识别六边形网格
- 自定义 OCR 识别数字和格子类型
- 对当前盘面做 3-step solving
- 可自动执行点击
- 还能把当前识别到的状态保存成 `*.hexcells`

对我们最有价值的地方：

- 它证明了：**“实时识别官方游戏窗口 -> 求解 -> 自动操作” 这条路也是可行的**
- 它也间接证明了：OCR/视觉部分往往比逻辑求解更脆弱，因为 README 专门写了不少识别条件和失败案例

注意事项：

- 它更像“完整自动化工具”，不是一个最小求解核心
- 如果一开始就照它那条路做，工程复杂度会明显变大

### 2.3 结论

所以对“是否已有开源案例”的回答是：

- **有**
- 而且刚好分成两条典型路线：
  - `SixCells`：先建模求解
  - `HexSolver`：直接从真实游戏画面抓状态再求解

我没有查到一个比这两者更新、且同样完整、同样公开、同样被社区反复引用的主流开源参考实现。这个结论是基于本次搜索结果的保守判断，不排除有零散小项目没被搜到。

## 3. 先明确我们要做的是哪一种“求解器”

这一步非常关键。因为“求解器”其实可能指三个完全不同的东西。

### 3.1 类型 A：纯逻辑求解器

输入：

- 一个已经结构化的盘面描述

输出：

- 哪些未知格一定蓝
- 哪些未知格一定黑
- 或者整个唯一解

这是最适合先做的版本。

### 3.2 类型 B：游戏辅助求解器

输入：

- 官方游戏当前画面

输出：

- 当前可下的一步
- 或者所有必然步

它本质上是：

- 图像识别器
- 盘面重建器
- 逻辑求解器

三者的组合。

### 3.3 类型 C：全自动代打器

输入：

- 官方游戏窗口

输出：

- 自动点击直到通关

这是 B 的再上一层，不该作为第一阶段目标。

## 4. 为什么不建议第一步就做 OCR

因为对 `Hexcells Infinite` 来说，真正难的往往不是“求解”，而是“拿到干净、稳定、完整的盘面状态”。

具体原因：

- OCR 需要先识别网格、坐标、颜色、数字、线头方向、覆盖提示等
- 分辨率、窗口缩放、转场动画、颜色变化都会增加脆弱性
- `HexSolver` README 里也明确提到要在特定窗口条件下识别，且会遇到一些布局失败场景

相比之下，纯逻辑求解的输入如果已经结构化：

- 可以直接写单元测试
- 可以对单条规则逐个验证
- 可以更快定位“规则错了”还是“算法错了”

所以路线应当是：

- 先把 `board -> constraints -> forced moves` 做对
- 再把 `screenshot -> board` 接上去

## 5. 第一阶段最推荐的输入格式

### 5.1 首选：`.hexcells`

理由很简单：

- `SixCells` 已经定义了公开、稳定、容易解析的 `.hexcells` 格式
- Steam 官方后来直接支持了由 `SixCells` 编辑器创建的自定义关卡
- 这意味着：**`.hexcells` 是现成的测试资产格式**

`SixCells` README 给出的格式信息非常有用：

- UTF-8 文本
- 固定头部
- 33x33 的网格表示
- 用字符区分黑格、蓝格、列线索
- 用 `+ / c / n` 之类的标记表达普通、连续、不连续提示

这对我们第一版特别友好。

### 5.2 不推荐第一阶段直接逆向官方随机局存档

原因：

- 社区讨论里提到，随机生成关卡的存档看起来主要保存种子和当前格子状态，而不是完整关卡几何与提示值
- 开发者自己也说过，内部是自定义数组结构，外部原始 Unity 资源格式并不适合直接拿来编辑

这说明两件事：

1. 逆向官方内部格式不是最短路径
2. 即使拿到随机局种子，没有生成器实现，也不等于能还原整个盘面

所以第一阶段别把力气花在这里。

## 6. 推荐的整体架构

我建议把项目拆成 5 层。

### 6.1 层 1：盘面领域模型

先定义一个和 UI、OCR、求解器都解耦的内部表示。

建议对象：

- `Board`
- `Cell`
- `UnknownCell`
- `ClueCell`
- `LineClue`
- `OverlayClue`
- `GlobalClue`

建议核心字段：

- 六边形坐标或唯一 ID
- 邻接关系
- 当前状态：未知 / 已判蓝 / 已判黑 / 预揭示
- 线索类型：普通 / 连续 / 非连续 / `?`
- 线索作用域：邻域 / 线段 / 覆盖范围 / 全局
- 线索目标集合：这条约束到底作用到哪些格

最重要的设计原则：

**所有线索最终都应落成“对一组布尔变量的约束”。**

### 6.2 层 2：输入适配器

第一版先只做两个：

- `.hexcells` 解析器
- 内部 JSON/测试 DSL 解析器

其中测试 DSL 很重要，因为它能让我们写最小规则样例：

- 一个只测试 `{n}` 的 7 格盘
- 一个只测试 `-n-` 的线段
- 一个只测试 overlay 的小盘

这样调试速度会快很多。

### 6.3 层 3：约束编译器

它的职责是把盘面对象编译成统一约束系统。

未知格变量：

- 对每个未知格定义一个布尔变量 `x_i`
- `x_i = 1` 表示蓝
- `x_i = 0` 表示黑

约束类别：

- 普通数字：`sum(S) = n`
- 全局剩余：`sum(AllUnknown) = remaining`
- 连续提示 `{n}`：`sum(S) = n` 且蓝格在某个顺序上只形成一个连续块
- 非连续提示 `-n-`：`sum(S) = n` 且蓝格不能形成唯一连续块
- 内嵌线头：对子区间重复上面约束
- overlay：对覆盖集合做精确计数

这里要特别注意顺序模型：

- 黑色提示格周围是环序
- 线头是线序
- 两者的连续性定义不一样，不能共用一套偷懒逻辑

### 6.4 层 4：求解后端

这里我建议分两类，不要一开始只押一种。

#### A. 规则传播器

写一批便宜、好解释、好调试的确定性规则：

- 剩余全满/全空
- 共享集合的子集差集推理
- 连续段上下界
- `remaining` 收尾
- 线段分块计数

好处：

- 很适合做提示系统
- 很适合做人类可读解释
- 很适合快速发现实现错误

#### B. 精确求解后端

我更建议用现代的约束求解器做兜底，比如：

- `OR-Tools CP-SAT`
- 或 `MILP`（`PuLP + HiGHS/SCIP/CBC` 之类）

为什么要有它：

- 可以快速验证当前盘面是否可满足
- 可以判断是否唯一解
- 可以找出“必然为蓝/黑”的格
- 可以做回归测试基准

如果只看“最稳妥、最有先例”的路线，`MILP` 是已经被 `SixCells` 验证过的。

如果看“现代工具链、布尔约束表达力、后续扩展”，`CP-SAT` 也很合适。

我的偏好是：

- **工程首选：`CP-SAT`**
- **参考实现首选：研究 `SixCells` 的 `MILP` 思路**

### 6.5 层 5：解释与交互

这层完全可以后做。

可能产物：

- CLI：输出所有 forced cells
- TUI/GUI：显示下一步
- explanation engine：给出某步的原因
- screenshot importer：从截图重建盘面
- live assistant：辅助官方窗口

## 7. “求解”本身应该怎么定义

这里最好一开始就定清楚，不然很容易目标发散。

### 7.1 最简单的机器目标

给定当前部分已开的盘面，返回：

- 当前所有一定为蓝的格
- 当前所有一定为黑的格

这是最合适的第一目标。

### 7.2 如何判断某格是不是“必然”

标准做法：

1. 建立当前盘面的完整约束模型
2. 检查是否存在满足解
3. 对某个未知格 `x`
   - 试 `x = 1` 是否可满足
   - 试 `x = 0` 是否可满足
4. 若只有一种取值可满足，则该格是 forced

这其实就是很多逻辑游戏求解器最稳的核心定义。

### 7.3 如果想要“下一步提示”

可以有两种口径：

- 机器口径：任何 forced move 都算下一步
- 人类口径：只返回能被“简单规则”解释的一步

建议第一阶段只做机器口径。

原因：

- 更容易验证正确性
- 更容易覆盖复杂盘面
- 不会被“这步人类看不出来算不算解出来”拖住

## 8. 建议的阶段划分

### 阶段 0：规则样例与测试资产

交付物：

- 一组最小盘面测试样例
- 每个规则至少一个正例、一个反例

必须覆盖：

- 普通黑格数字
- 黑格 `{n}`
- 黑格 `-n-`
- 普通线头
- 线头 `{n}`
- 线头 `-n-`
- overlay
- `?`
- `REMAINING`
- 内嵌线头

### 阶段 1：内部模型 + `.hexcells` 解析

交付物：

- 能读 `.hexcells`
- 能建立内部 `Board`
- 能把所有约束对象列出来

验收标准：

- 读入一个关卡后，能打印出所有未知格、线索集合、邻接关系、线段关系

### 阶段 2：精确求解后端

交付物：

- 判断盘面是否可满足
- 判断是否唯一解
- 返回所有 forced cells

验收标准：

- 至少能解一批 `.hexcells` 关卡
- 对明显矛盾盘面能报 unsat

### 阶段 3：规则传播器

交付物：

- 一组不依赖全局搜索的基础规则
- 可输出“这一步是由哪条规则推出的”

验收标准：

- 在简单关卡上，规则传播器单独就能推进不少步
- 在复杂关卡上，和精确求解结果一致

### 阶段 4：提示系统

交付物：

- `hint` 模式
- `solve-step` 模式
- `solve-all` 模式

这时项目就已经很好用了。

### 阶段 5：截图/OCR 输入

交付物：

- 从截图恢复盘面
- 调求解核心
- 输出下一步或全部 forced cells

只有到这一步，才值得讨论：

- 自动点击
- 实时窗口跟踪
- 完整游戏代理

## 9. 对官方 `Infinite` 随机局，路线该怎么选

这是最容易选错的地方。

### 9.1 如果目标是“先证明 solver 能工作”

那就不要先碰官方随机局。

先做：

- `.hexcells`
- 自定义测试关卡
- 已知结构化盘面

### 9.2 如果目标是“最后要辅助 Infinite 随机生成关卡”

那也建议分两段：

1. 先做纯逻辑核心
2. 再做截图识别或窗口抓取

原因：

- `Infinite` 随机局的主要难点是状态提取，不是规则本身
- `2.0 Update` 新增的 `hard mode` 影响的是生成难度，不是底层语义

所以 hard mode 不需要特殊 parser，只需要 solver 足够强。

## 10. 一个务实的技术选型建议

如果今天就开工，我会这样选：

### 10.1 语言

优先：

- `Python`

理由：

- 跟 `SixCells` 参考生态接近
- 适合快速建模和测试
- 适合接 `OR-Tools` / `PuLP`
- 后续接 OCR 也方便

如果将来非常在意性能，再把约束核心迁移到别的语言。

### 10.2 约束后端

优先：

- `OR-Tools CP-SAT`

备选：

- `PuLP + HiGHS/SCIP/CBC`

### 10.3 项目结构

建议像这样拆：

```text
src/
  hexcells/
    model/
    parser/
    constraints/
    solver/
    explain/
    io/
tests/
  fixtures/
    hexcells/
    minimal/
```

### 10.4 最先写的测试

不是整关回归，而是最小规则测试。

例如：

- “一个 `{3}` 环上 6 邻位，已知 2 蓝 1 黑，剩余 forced 是什么”
- “一条 `-4-` 线段在给定边界后哪些格不可能”
- “overlay 与 `remaining` 交叉后哪些格 forced”

## 11. 最大风险在哪里

### 11.1 最大风险不是算法，而是输入

如果目标是官方游戏实时辅助，真正最脆弱的是：

- 怎么稳定拿到盘面
- 怎么识别线头/数字/类型
- 怎么应对不同分辨率和 UI 状态

### 11.2 第二个风险是连续性语义实现错

尤其是：

- 黑格 `{n}` / `-n-` 的环形连续性
- 线头 `{n}` / `-n-` 的线性连续性
- 空洞是否打断线

这部分必须靠非常小的单元测试钉死。

### 11.3 第三个风险是把“会求解”误做成“会解释”

“找 forced cells”和“给出漂亮的人类解释”不是一个难度层级。

建议顺序：

- 先正确
- 再可用
- 最后再优雅解释

## 12. 我认为最合适的起步方案

如果要我现在给一个最具体的落地建议，就是下面这套：

1. 用 `Python`
2. 定义内部 `Board/Clue/Constraint` 模型
3. 先支持 `.hexcells`
4. 先做 `CP-SAT` 或 `MILP` 精确求解
5. 暂时只输出：
   - `is_satisfiable`
   - `is_unique`
   - `forced_blue`
   - `forced_black`
6. 用最小规则样例和 `.hexcells` 关卡做回归
7. 等核心稳定后，再评估是否做 OCR 或官方窗口助手

这条路线的优点：

- 最短路径能做出“真的能解”的东西
- 最容易测试
- 最容易验证规则理解有没有错
- 最不容易被图像识别细节拖死

## 13. 和“生成器”要分开看

求解器和生成器不是同一个难度级别。

开发者在关卡格式讨论里明确提到过一个现实问题：

- 用户自制关卡/生成关卡的难点，不只是放格子
- 更难的是保证线索足够、布局合法、并且盘面能被正确解出

所以如果以后想做：

- 关卡校验器
- 关卡生成器
- 可解性检查器

那正好都建立在求解器之上。

换句话说：

**先有 solver，后谈 generator，顺序是对的。**

## 14. 资料结论小结

本次调研后的判断是：

- 开源案例已经存在，不需要从零猜路
- `SixCells` 证明了纯逻辑求解路线是可行的
- `HexSolver` 证明了 OCR + 自动操作路线也是可行的
- 但如果目标是稳、快、可验证，第一阶段仍然应该先做结构化盘面的逻辑核心
