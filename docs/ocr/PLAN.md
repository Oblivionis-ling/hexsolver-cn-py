# OCR 优化计划

当前阶段先暂停 UI 外观改造，把重点放在 OCR 稳定性上。目标不是“让通用 OCR 硬读整张图”，而是把 `Hexcells Infinite` 的线索识别拆成更小、更可控、更容易评估的步骤。

## 1. 当前问题判断

目前 OCR 的主要难点不是单纯“模型不够强”，而是识别对象太特殊：

- 外侧行线索很小，位置分散，并且有三个方向。
- `{n}`、`-n-`、普通数字的语义不同，识别错一个符号就会让求解器约束错误。
- 格内提示和外侧行提示的字号、颜色、背景、倾斜角度并不完全一致。
- 截图分辨率、缩放、窗口边框、抗锯齿都会影响模板匹配。
- 通用 OCR 即使读出了文本，也不一定能正确绑定到对应的行或格子。

所以 OCR 优化应该优先解决“候选区域是否正确”和“候选结果是否可信”，再考虑换更大的 OCR 模型。

## 2. 推荐技术路线

### 2.1 先做可评估的 OCR 测试集

需要把调试从“看起来准不准”变成“每张图有多少项识别正确”。

建议建立一套后续可上传的结构：

```text
tests/
  ocr_cases/
    images/             脱敏后的测试截图
    labels/             人工标注的 JSON 文件
    reports/            每次评估生成的报告，不必全部提交
```

标注内容建议包括：

- 顶部 `REMAINING` 的真实数字。
- 每个已知格的真实线索。
- 每条外侧行线索的真实内容和方向。
- 如果某张截图存在特殊问题，要记录问题说明。

### 2.2 按目标类型拆 OCR

不要用一套 OCR 逻辑处理所有文字。更好的拆法是：

- `REMAINING`：只在顶部或右上区域找整数，允许使用 RapidOCR。
- 格内线索：根据格子中心裁剪小图，再做模板匹配或小分类器。
- 外侧行线索：先由棋盘几何推出行线索锚点，再围绕锚点裁剪候选图。

这样每个 OCR 子任务都有明确输入范围，误识别会少很多。

### 2.3 几何优先于模型

外侧行线索最值得先优化几何定位。

具体做法：

- 从棋盘轴坐标推导三组行方向。
- 为每条边界行计算理论线索锚点。
- 按方向生成候选裁剪框，而不是在整图里盲找。
- 对倾斜方向的裁剪框做旋转归一化，让文字尽量水平后再识别。
- 导出每个候选裁剪图，方便人工快速检查定位是否偏移。

只要裁剪区域稳定，普通模板匹配的准确率也会明显提高。

### 2.4 用候选约束降低误判

`Hexcells` 的线索不是任意文本，识别时应主动限制候选集合。

候选规则：

- 黑格邻域线索只可能是 `0` 到 `6`，以及 `{n}`、`-n-`。
- 蓝格范围线索通常是普通数字，范围由半径 2 内可玩格数量决定。
- 外侧行线索最大值不应超过这条行的格子数量。
- `REMAINING` 是非负整数，且不应超过未知格数量。

每个 OCR 结果都应该给出：

- 文本候选
- 置信分数
- 来源方式
- 对应截图框
- 是否通过规则校验

低可信或不满足规则的结果不要自动写入求解器，只显示为待确认候选。

## 3. OCR 方案选择

### 3.1 保留 RapidOCR 作为基线

RapidOCR 适合继续保留，因为它轻量、离线、已经接入项目，并且对整图文字框候选有帮助。

但它不应该独自负责最终答案。对很小、倾斜、符号化的行线索，RapidOCR 更适合做“候选发现”，不适合无条件自动填入。

### 3.2 强化模板 OCR

短期最值得投入的是模板 OCR。

原因：

- 游戏字体固定。
- 线索字符集合很小。
- 可结合几何裁剪和候选约束。
- 结果更容易解释和调试。

模板 OCR 的下一步可以做：

- 多尺度模板匹配。
- 二值化、反色、锐化、去背景的多预处理版本。
- 对 `{`、`}`、`-`、数字分别打分，再组合成合法线索。
- 为不同截图缩放自动选择最佳模板尺度。

### 3.3 PaddleOCR 可以作为对照实验

如果愿意接受更重的依赖，PaddleOCR 值得测试。它的文本检测、方向分类和识别能力通常比轻量 OCR 更强，可能对外侧线索候选框更友好。

但我不建议马上把 PaddleOCR 作为主方案，因为：

- 安装体积和依赖更重。
- 推理速度可能更慢。
- 对 `{n}`、`-n-` 这种游戏符号线索仍然可能不稳定。
- 最终仍需要候选约束和人工确认机制。

更合理的方式是把 PaddleOCR 做成可选后端，用同一批测试图和 RapidOCR、模板 OCR 对比。

### 3.4 EasyOCR 优先级较低

EasyOCR 可以试，但不是我当前首选。它依赖较重，对普通场景文字不错，但对 `Hexcells` 这种小字号符号化线索未必比 PaddleOCR 更适合。

### 3.5 未来可以训练小模型

如果后面有足够标注图，可以训练一个很小的专用分类器或 CRNN，只识别 `0-19`、`{n}`、`-n-`、`?` 等有限类别。

这条路线长期很稳，但前提是先有高质量标注集。现在不建议先训练，因为没有评估集时容易“模型看起来变强了，实际错误更隐蔽”。

## 4. 我可以做什么

我可以直接在项目里完成这些工作：

- 新增 OCR 回归评估脚本，输出每张图的识别命中率。
- 设计并实现 `labels/*.json` 标注格式。
- 把 `detector.py` 拆成更清晰的阶段：棋盘定位、候选裁剪、OCR、候选绑定、置信过滤。
- 为每张截图导出行线索、格内线索、`REMAINING` 的调试裁剪图。
- 改进外侧行线索的几何锚点和旋转归一化。
- 强化模板 OCR 的多尺度、多预处理、多候选打分。
- 增加“只自动填高可信结果，低可信显示候选”的策略。
- 接入 PaddleOCR 做可选实验，并用同一套测试集比较效果。

## 5. 你可以做什么

你最有价值的工作是提供真实样本和人工判断，这部分机器很难替代：

- 尽量提供原始分辨率截图，不要二次压缩。
- 同一批测试图尽量保持游戏窗口缩放一致。
- 选 10 到 30 张有代表性的截图作为 OCR 测试集。
- 给这些截图标注真实 `REMAINING`、行线索和格内线索。
- 每次 OCR 改动后，指出仍然错得最明显的 3 到 5 张图。
- 决定自动填入策略要保守还是激进。

我建议自动填入策略先保守：宁可少填，也不要把错线索送进求解器。等回归测试稳定后，再逐步放宽自动填入。

## 6. 下一步落地顺序

第一步：建立 OCR 测试与调试输出。

- 增加标注 JSON 格式。
- 增加评估脚本。
- 导出每个候选裁剪图。

第二步：优化外侧行线索定位。

- 按棋盘几何生成三方向行线索锚点。
- 对裁剪框做方向归一化。
- 让每条行线索都有可回看的候选来源。

第三步：强化模板 OCR。

- 做多尺度匹配。
- 加入多种预处理。
- 用合法线索候选集合做最终筛选。

第四步：对比可选 OCR 后端。

- RapidOCR 作为默认基线。
- PaddleOCR 作为实验后端。
- 模板 OCR 作为游戏线索主识别器。

第五步：把 OCR 结果接入求解安全检查。

- 高可信结果自动填入。
- 中低可信结果只显示候选。
- 求解无解时反向提示最可疑 OCR 项。

## 7. 当前结论

我认为最好的 OCR 方向是“几何裁剪 + 专用模板识别 + 候选约束 + 回归评估”，而不是直接换一个更大的通用 OCR。

通用 OCR 可以做辅助，但这个项目真正的稳定性会来自两个东西：第一，线索候选区域定位准；第二，所有识别结果都经过游戏规则校验。这样后面 UI 再怎么改，求解器吃到的数据都会更可信。
