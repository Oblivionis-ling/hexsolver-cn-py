# 求解算法说明

这份文档总结 `0.4.3` 起沿用至 `0.6.2` 的求解计算与解释逻辑，重点对应 [solver.py](../../src/hexsolver_cn/solver.py) 中已经实现的约束建模、推理和可核查理由生成流程。`0.5.0` 只增加 Windows 单文件封装；`0.6.1` 与 `0.6.2` 只调整推理说明区、次要侧栏信息、手动图例和行线索可见性，均未修改本文件描述的核心算法。

## 1. 输入与目标

求解器的输入是一个 `Board`：

- 棋盘上每个格子的轴坐标 `coord`
- 每个格子的状态：
  - `hidden`：未知格
  - `blue`：已知蓝格
  - `black`：已知黑格
  - `grey/outside`：不可用
- 已识别或人工确认的线索：
  - 黑格邻域线索
  - 蓝格范围线索
  - 外侧行线索
  - 顶部 `REMAINING`

求解器的输出不是“直接把整盘解完”，而是：

- 当前一定可以开的格子
- 当前一定必须标黑的格子
- 每一步为什么成立

也就是说，输出的是“**当前必然步**”。

## 2. 棋盘变量表示

在约束层里，只有未知格 `hidden` 会被建成布尔变量：

- `1` 表示这个未知格最终是蓝格
- `0` 表示这个未知格最终是黑格

已知蓝格和已知黑格不会再建变量，而是直接作为常量参与约束：

- 已知蓝格视为常量 `1`
- 已知黑格 / 灰格 / 不存在位置视为常量 `0`

## 3. 三类线索的约束对象

### 3.1 黑格线索

黑格线索只约束它的 **6 个直接邻居**。

- 普通数字 `n`：邻居蓝格总数等于 `n`
- `{n}`：邻居蓝格总数等于 `n`，并且这些蓝格在 6 邻域环上必须连续
- `-n-`：邻居蓝格总数等于 `n`，并且这些蓝格不能形成一个连续块

黑格是环形邻域，所以 `{n}` / `-n-` 都按 **循环序列** 处理。

### 3.2 蓝格线索

蓝格线索约束它 **半径 2 内的全部可玩格**，不包含它自己。

- 只支持普通数字 `n`
- 约束含义：范围内蓝格总数等于 `n`

### 3.3 外侧行线索

每条外侧行线索约束一整条线上所有可玩格。

- 普通数字 `n`
- `{n}`
- `-n-`

行线索不是环形，所以 `{n}` / `-n-` 按 **线性序列** 处理。

## 4. 约束规格化

求解器会先把所有线索统一转换成 `ConstraintSpec`：

- `label`：用于输出理由
- `clue_type`：`count / consecutive / nonconsecutive`
- `number`
- `coords`：这条线索实际约束到的格子坐标序列
- `cyclic`：是否按循环序列处理

这样后面不再区分“它来自黑格、蓝格还是外侧行”，而是按统一的约束模型推理。

## 5. 第一层：局部确定性推理

求解器优先做不用全局搜索的局部推理。

### 5.1 计数补满规则

对任意一条线索，统计：

- `known_blue`：当前已经确定为蓝的格子数
- `hidden`：当前仍未知的格子集合
- `need = number - known_blue`

然后有两种最基本的必然结论：

- 如果 `need == 0`
  - 说明需要的蓝格已经凑够
  - 那么这条线索里剩下的所有未知格都必须判黑

- 如果 `need == len(hidden)`
  - 说明剩下所有未知格都得拿来补蓝
  - 那么这些未知格都必须判蓝

输出理由会同步列出：

- 线索的完整名称与要求
- 已知蓝格数量和坐标
- 未知格数量和坐标
- `number - known_blue = need` 的具体算式
- 目标格为什么不能取另一种颜色

### 5.2 连续 / 非连续排列推理

对 `{n}` 或 `-n-`，会枚举这条线索允许的所有局部排列。

如果某个未知格在 **所有合法排列** 里都只能是蓝，或都只能是黑，那么它就是必然步。

这里分两类：

- `{n}`：
  - 直接枚举所有连续块位置
- `-n-`：
  - 枚举所有蓝黑组合
  - 过滤掉那些“蓝格刚好形成单一连续块”的情况

理由会给出合法排列总数、最多四个“未知格取蓝坐标”的排列样例，以及目标格在所有排列中为蓝/黑各出现多少次。这样“所有排列都一样”可以直接由统计核对。

### 5.3 子集差分规则

如果两条线索的未知格集合满足：

- `A_hidden ⊆ B_hidden`

那么可以比较它们各自还需要的蓝格数：

- 若 `A_need == B_need`
  - `B - A` 这部分差集不可能再提供蓝格
  - 差集全黑

- 若 `B_need - A_need == len(B - A)`
  - 差集里的所有格都必须拿来补蓝
  - 差集全蓝

理由会分别展开 A、B 的线索、已知蓝格数、未知集合、需求计算、`B - A` 坐标和需求差公式。

这条规则对很多重叠线索非常有效。

### 5.4 REMAINING 全局补满规则

如果顶部 `REMAINING` 已知：

- `remaining_blue == 0`
  - 所有未知格全黑

- `remaining_blue == hidden_count`
  - 所有未知格全蓝

理由会列出全盘未知格坐标，并直接展示 `remaining_blue` 与 `hidden_count` 的比较。

## 6. 第二层：全局约束求解

如果局部规则没有推出任何必然步，就进入全局模型。

当前项目使用的是 **OR-Tools CP-SAT**。

## 7. CP-SAT 模型怎么建

### 7.1 基本计数约束

对每条 `ConstraintSpec`，都会生成：

```text
sum(sequence) == number
```

其中 `sequence` 是这条线索对应的 0/1 序列。

### 7.2 `{n}` 连续约束

如果是连续线索 `{n}`，会额外引入“连续块起点”布尔变量 `start_i`。

约束逻辑是：

1. 只能选择一个起点
2. 被这个起点覆盖到的那一段格子必须为蓝
3. 其他格子必须为黑

线性行线索与黑格环形线索的区别，只体现在“覆盖索引”是否循环。

### 7.3 `-n-` 非连续约束

如果是非连续线索 `-n-`，在已经有 `sum(sequence) == number` 的前提下，再禁止出现长度刚好为 `n` 的完整连续块。

也就是对每个可能的长度为 `n` 的窗口，加：

```text
sum(run) <= n - 1
```

含义是：

- 你可以有 `n` 个蓝格
- 但它们不能正好全部连成一整块

### 7.4 REMAINING 约束

如果顶部剩余蓝格数已知，再加：

```text
sum(all_hidden_variables) == remaining_blue
```

## 8. 第三层：唯一性 forced move 检查

全局模型可行之后，求解器不会直接返回某个完整解，而是逐个检查未知格是否“被唯一确定”。

对每个未知格 `x`：

1. 假设 `x = 蓝`
2. 假设 `x = 黑`
3. 分别检查模型是否仍可行

结论：

- 如果“蓝可行、黑不可行”
  - 这个格必须判蓝
- 如果“黑可行、蓝不可行”
  - 这个格必须判黑
- 如果“两边都可行”
  - 当前还不是必然步

这一步给出的就是“全局唯一性推理”。

### 8.1 `0.4.3` 的全局反证解释

只写“假设为蓝/黑会无解”仍然不够核查，因此 `0.4.3` 在发现 forced move 后，会再构造一个带 assumptions 的证明模型：

1. 每条黑格、蓝格或行线索由一个独立的启用字面量控制。
2. 顶部 `REMAINING` 也作为独立条件加入。
3. 错误颜色假设作为最后一个 assumption 加入。
4. 当模型确定无解时，读取 CP-SAT 的 `SufficientAssumptionsForInfeasibility`。
5. 将返回的线索逐条转换成当前盘面状态：目标数、已知蓝格、未知格、还需蓝格和坐标集合。
6. 再检查相反颜色假设，确认完整约束至少存在一个可行解。

这得到的是“一组与错误假设合在一起足以无解的关键条件”。它是有效的充分冲突集合，但不保证是数学上最小的集合，也不宣称是唯一证明。界面中的说明会明确写出这个边界。

为了避免每次点击都为整盘所有 forced move 重复提取冲突条件，`next_step()` 在全局阶段按稳定坐标顺序找到第一条必然步后就停止；公开的 `solve()` 仍可返回全部当前必然步。

## 9. 为什么求解器是两段式的

当前实现不是一上来就把所有未知格丢进 SAT 全搜，而是：

1. 先做局部规则
2. 局部无果时再做全局 forced move

这样做的好处是：

- 理由更自然，更像人类解题过程
- 一般局面下更快
- 输出解释更可读

`0.4.3` 的每类局部理由都由实际参与计算的数据生成；全局理由则由同一组 CP-SAT 约束及其冲突集合生成，不另写一套可能漂移的“解释模型”。

## 10. 当前实现的边界

### 10.1 优点

- 已覆盖 Infinite 常用核心规则
- 支持黑格、蓝格、行线索、REMAINING
- 支持 `{n}` 和 `-n-`
- 支持带具体坐标、算式、排列统计的局部解释
- 支持错误假设、充分冲突条件和反向可行性检查组成的全局唯一性解释

### 10.2 当前限制

- 还没有实现更强的命名式高阶逻辑链推理
- 没有做“整盘最优解释排序”
- 全局冲突条件是充分核心，不保证最小或唯一
- 结果是“当前必然步及其可核查证据”，不是完整的人类证明树
- OCR 错误会直接影响约束和解释正确性

## 11. 如果后续继续升级

下一步最值得加强的方向通常有三类：

1. 更强的 OCR 与线索置信管理
2. 更强的局部推理规则库
3. 将充分冲突核心进一步转换为更短的代数推导或命名式人类规则链
